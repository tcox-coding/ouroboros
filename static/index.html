LoRA library

What automatic runs pick from

The loop picks from this same catalog: it shortlists by description across everything installed, then compares the shortlist's example renders against your reference.

The scan below is only the fallback for setups without a classified catalog.

Add poses an image, several, or a whole folder

Any picture of a person in the pose you want: a screenshot, a photo, another character. Its skeleton (body, hands and face points) is extracted with DWPose and saved; only the pose is used, never the character. The LLM also writes a short description of the pose for the prompt writer and the judge. Pick it in Generate's Pose tile: the character comes from the subject, the pose from here.

Add styles an image, several, or a whole folder

Any picture drawn in the look you want. The LLM writes its style tags (line work, shading, palette, medium) and, unless you name it, a name. Pick it in Generate's Style tile (or let the AI pick one): its image drives a style-transfer IP-Adapter and its tags the prompt; the judge scores style against it.

Add characters an image, several, or a whole folder

A clear picture of the character, ideally full body. The LLM writes the character's tags (hair, eyes, outfit, colours) and, unless you name it, a name. Pick it in Generate's Subject tile (or let the AI pick one, which it only does when the description clearly matches): its image drives the character IP-Adapter and its tags the prompt; the judge scores identity against it.

Loop defaults

img2img from the reference below the minimum denoise, or inpainting the reference, mostly copies it. Keep these on to get a new image of the same character.

Judging

Every judge call starts a fresh context. Accuracy drops as a prompt grows (well before the window is full) and the middle of a long prompt is recalled worst, so the rubric, rules and reference go first, a task reminder goes last, and older rounds are folded into a short AI-written summary to stay under the budget.

Checkpoint and LoRAs

LoRAs outside these folders (such as a hand-fix LoRA) stay as saved in the workflow. The checkpoint's family (Pony, Illustrious, Flux) comes from its name; LoRAs made for another family are skipped. Flux checkpoints can't run in this SDXL workflow. The Civitai key is under API keys above.

Auto-fix

The judge model looks at the image on its own (no reference) for flaws: finger counts, impossible joints, extra limbs, distorted proportions, melted faces, fused clothing, artifacts. It ignores what the prompt asks for. Each flaw is repainted where it is (hands with the hand refiner), then a before/after review keeps the result only if it is clearly better. The original is always kept. On Generate it's a checkbox under Generation; in History, a button on each image.

Upscale

The image (its auto-fixed version if it has one) is enlarged, then redrawn lightly at the larger size with the checkpoint, LoRAs, prompt and seed that made it, the way hires fix works. The original is always kept. On Generate it's a checkbox under Generation; in History, an Upscale button by each image. 1.5× of an SDXL image is ~1.5k px; 2× takes roughly three times as long.

Pose ControlNet and hand refiner

Both use the xinsir ControlNet Union (SDXL) in openpose mode. HandRefiner's own ControlNet is SD 1.5 only and can't attach to an SDXL checkpoint, so hands are refined the same way natively: DWPose fits each hand with a clean five-finger skeleton, and just that hand is repainted at 1024 px following it. The automatic pass keeps the refined image only if a fresh judge look scores it at least as high; the button on a finished run always keeps both.
